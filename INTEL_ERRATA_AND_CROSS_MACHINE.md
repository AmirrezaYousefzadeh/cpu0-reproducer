# Distinguishing a particular system from a processor-model issue

A processor design or microcode issue remains possible. A single machine's affinity-dependent application crash does not identify the root component. A bad CPU sample, board/power settings, firmware, kernel interaction or software/toolchain defect can produce overlapping symptoms. CPU 0 can also have a different platform/OS role from another core. The current case must not be described as proof that all 285K processors are defective.

Intel publishes characterized Arrow Lake errata in specification update 834774. The reviewed online revision is 023, dated September 2026. Examples include incorrect data around deeper idle-state activity (ARL036), unexpected indirect-branch behavior (ARL047), and core hangs during deeper idle-state transitions (ARL037). The summary marks the first two Fixed for the S 8P+16E line and ARL037 Planned Fix. Those labels do not identify the minimum BIOS/microcode revision for this motherboard. A whole-core hang is not the same observed symptom as this application's Signal 11. None of these entries has been established as the explanation here. [Intel details](https://edc.intel.com/content/www/us/en/design/products/platforms/details/arrow-lake-s/core-ultra-200s-series-processors-specification-update/errata-details/), [status table](https://edc.intel.com/content/www/us/en/design/products/platforms/details/arrow-lake-s/core-ultra-200s-series-processors-specification-update/summary-tables-of-changes/).

The recorded family/model/stepping corresponds to CPUID C0662, which Intel identifies as ARL-S 8P+16E B0. The platform runs microcode 0x121. Intel's August 2026 release publishes 0x122 for ARL-S/HX 8P, signature 06-c6-02, platform mask 82, and references functional updates for the processor family. That newer revision has not been tested in this investigation. The release notes do not establish that it fixes this particular failure. [Intel identification](https://edc.intel.com/content/www/us/en/design/products/platforms/details/arrow-lake-s/core-ultra-200s-series-processors-specification-update/identification-information/), [Intel microcode release](https://github.com/intel/Intel-Linux-Processor-Microcode-Data-Files/releases/tag/microcode-20260811).

The current all-core screen uses the same input/toolchain sequentially on every allowed CPU, under one profile and unchanged memory settings. P-cores and E-cores have different performance, so their completion times alone are not a fault criterion. A timeout or setup error is inconclusive; a workload crash is recorded separately. One passing trial is a screen, not a health guarantee. Newly failing cores should be repeated with passing controls before assigning a persistent fault.

The most useful external comparison is a second 285K, ideally on another vendor's board:

1. Use the exact Git commit/fixture hashes, pinned OpenROAD/LibreLane and hashed PDK inputs. Record CPUID, BIOS, active microcode, kernel, power profile, core type and effective clocks.
2. Use Intel default CPU settings and JEDEC RAM first. Run `all_cores.py` or explicitly select comparable P/E-core groups. Preserve complete logs and telemetry, including passes. Repeat failures and controls on another boot.
3. If the same failure appears on independent 285K systems, keep model-wide firmware/design and common software explanations open. Try a different OpenROAD build/toolchain in a separately labelled experiment; a difference is evidence, not automatic attribution.
4. If possible, perform a controlled CPU/board swap. A fault that follows one processor across boards supports an individual processor problem. A fault that follows the board supports the platform path. Firmware/configuration must be held constant as far as practical.
5. Ask Intel/MSI to identify applicable errata and the required firmware mitigation, including whether the newer matching microcode should be tested through a vendor-supported update.

No cross-machine or component-swap result is currently available. The reproducible case is useful for a warranty investigation even while model-wide attribution remains unresolved. No memory, idle-state, voltage or microcode changes are made by this document or the all-core runner.
